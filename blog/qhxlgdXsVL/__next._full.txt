1d:T250f,<p><img src="https://assets.musecanto.com/uvxwY7KW9sGYbUfSojyke/sv-books/2026_05_25_editorimg_dee1ce5b-12f8-4d39-ac1e-0672357209c5.png" alt="111111111" loading="lazy" decoding="async">「MCP 已死，CLI 称王」——话太满，但<strong>方向不算错</strong>。</p>
<p>我 Cursor 里仍挂着 <strong>GitHub MCP</strong>，终端里也天天 <code>gh</code>。感受是：<strong>MCP 和 CLI 都会长期存在</strong>；而在「Agent 真正动手」这一层，<strong>CLI 正在变成更占优的默认选项</strong>——所以你看到一堆产品主动 <strong>CLI 化</strong>：不是抛弃智能，而是把执行层改回命令行擅长的形状。</p>
<p>下面用 <strong>MCP × CLI</strong>（GitHub 上即 <strong>GitHub MCP ×</strong> <code>gh</code>）把趋势、分工和边界说清楚。</p>
<hr>
<h2 id="为什么-ai-产品开始-cli-化">为什么 AI 产品开始 CLI 化</h2>
<p>大模型本质是 <strong>文本进、文本出</strong>；命令行也是 <strong>文本进、文本出</strong>。GUI 要截图、点按钮、猜布局；CLI 用 <code>help</code>、man、管道，和 Agent 同构。这不是怀旧，是 <strong>工程上更贴 Agent 的默认接口</strong>。</p>
<p><img src="https://assets.musecanto.com/uvxwY7KW9sGYbUfSojyke/sv-books/2026_05_25_editorimg_de05076d-f0c2-4c49-b86c-0621bd6d97ea.png" alt="222222222222222" loading="lazy" decoding="async">近一年里「把产品做成 CLI」的例子很集中：</p>
<ul>
<li><strong>GitHub</strong>：<code>gh</code> 本来就有；又推 <strong>Copilot CLI</strong>，和 IDE 里的 Agent 同一套肌肉</li>
<li><strong>Anthropic</strong>：<strong>Claude Code</strong>——对话外壳，执行落在终端</li>
<li><strong>OpenAI / 社区</strong>：ChatGPT CLI、各类 coding agent 终端入口</li>
<li><strong>Google</strong>：<strong>gws</strong> CLI 管 Workspace</li>
<li><strong>飞书</strong>：开源 CLI，200+ 指令，和 Agent Skills 一起卖</li>
<li><strong>Perplexity</strong>：CTO 公开讨论在生产里 <strong>减少 MCP、加大 API + CLI</strong>——争议点正是「执行层别再用胖 MCP 扛一切」</li>
</ul>
<details open>
<summary>关键判断</summary>
<p>CLI 化 ≠ 回到上世纪运维；</p>
<p>是把「<strong>可执行</strong>、<strong>可脚本化</strong>、<strong>可审计</strong>」的那一层暴露给 Agent，上面仍可挂自然语言、Slash、Canvas。</p>
</details>
<p>所以在Cursor中你用的 <code>/pr-review-canvas</code>、<code>/issue_to_fix_workflow</code> <strong>体验上可以挂在 MCP 生态里</strong>，但 Skill 里写明的往往是 <code>gh pr diff</code><strong>、</strong><code>gh issue view</code>——<strong>产品表面 MCP 化，执行层却在 CLI 化</strong>。这不是矛盾，是分层：MCP 管入口和目录，CLI 管高频动手。</p>
<p><img src="https://assets.musecanto.com/uvxwY7KW9sGYbUfSojyke/sv-books/2026_05_25_editorimg_c4f8aa21-7a03-4f77-bb63-d012f7a9093c.png" alt="image" loading="lazy" decoding="async"></p>
<hr>
<h2 id="当下-agent-里cli-为什么更占优">当下 Agent 里，CLI 为什么更占优</h2>
<p>相对「会话开始就加载几十个 MCP tool Schema」，CLI 在 AI 应用里有几条硬优势：</p>
<p><strong>省上下文（钱和智商一起省）</strong><br>
GitHub MCP 我本地 <strong>42 个 tool</strong>，描述约 <strong>47KB</strong>（粗算 <strong>~1.2 万 token</strong>）。一次 merge 可能只用 3 个，其余 <code>push_files</code>、<code>run_secret_scanning</code> 等仍占着窗口。社区里多 Server 叠加时出现 <strong>70%+ 上下文被 tool 文档吃掉</strong>、工具选择准确率 <strong>掉到 14% 以下</strong>，并不意外。<br>
<code>gh pr checks 128</code> 则不必预付 <code>gh release</code> 的说明书——<strong>按需</strong> <code>help</code>。</p>
<p><strong>可组合、可复跑</strong><br>
<code>gh pr diff | …</code>、<code>git</code> 管道，人和 Agent 复制同一条命令就能重跑。MCP 路径多一层 JSON 是否拼对，调试成本更高。</p>
<p><strong>训练与生态</strong><br>
模型在 man、Stack Overflow、shell 脚本上练得多；<code>gh</code> <strong>是 GitHub 官方 CLI</strong>，和「让 Agent 用熟工具」一致。</p>
<p><strong>认证与合规</strong><br>
<code>gh auth login</code> 一次，人机共用；企业审计对「终端里跑了什么」也熟。MCP 常是每个 Server 一套 PAT，Server 越多越碎。</p>
<p><img src="https://assets.musecanto.com/uvxwY7KW9sGYbUfSojyke/sv-books/2026_05_25_editorimg_e4ddffd7-7db8-49c7-9ff2-3051de2602ea.png" alt="333333333333" loading="lazy" decoding="async"></p>
<p>因此：<strong>不是 MCP 不能做这些事，而是同样的事用 MCP 做往往更贵、更脆、更难查</strong>——在「执行层」这一棒，CLI 当前明显更占优。</p>
<hr>
<h2 id="mcp-没退场它更适合另一层">MCP 没退场：它更适合另一层</h2>
<p>MCP 的价值要放在 <strong>「协议 / 插头 / 能力目录」</strong>，而不是和 CLI 抢每一次 merge。</p>
<ul>
<li><strong>跨客户端统一</strong>：同一 GitHub Server 给 Cursor、Claude Desktop 用——工具发现、能力声明</li>
<li><strong>人主要在对话窗、少切终端</strong>：<code>issue_write</code>、<code>create_pull_request</code>、<code>get_file_contents</code></li>
<li><strong>跨 repo / 组织检索</strong>：<code>search_code</code>、<code>search_pull_requests</code>——不必先拼一长串 shell</li>
<li><strong>复杂 API 一次 Structured 调用</strong>：<code>pull_request_read</code> 带 <code>get_review_comments</code>、分页等</li>
<li><strong>MCP Prompt 编排</strong>：如 <code>issue_to_fix_workflow</code>——流程入口在协议层，<strong>步骤里仍可调用 gh</strong></li>
</ul>
<p><strong>MCP 被说「喂胖」</strong>，通常是因为 <strong>用 MCP 承担了 CLI 更擅长的执行层</strong>：每天本地的 list PR、看 CI、merge 都走 <code>merge_pull_request</code>，等于高频动作也为 42 个 tool 买单。</p>
<p><img src="https://assets.musecanto.com/uvxwY7KW9sGYbUfSojyke/sv-books/2026_05_25_editorimg_d1609750-9ef0-4484-b55f-96dbf975c929.png" alt="image" loading="lazy" decoding="async"><strong>仍值得用 MCP 的场景：</strong></p>
<details open>
<summary>关键判断</summary>
<p>MCP 适合「接进来、被发现、在 IDE 里结构化调用」；CLI 适合「真干活、高频、本地仓库、要能复跑」。趋势是执行层 CLI 化，MCP 收窄到插头角色。</p>
</details>
<hr>
<h2 id="怎么选cli-优先mcp-补位">怎么选：CLI 优先，MCP 补位</h2>
<ul>
<li><strong>动作是否每天都在本机仓库发生？</strong> 是 → <strong>CLI（gh）优先</strong>；只读远端、跨 repo → <strong>MCP 补上</strong>。</li>
<li><strong>要不要给人一条可复制命令？</strong> 要 → <strong>CLI</strong>；只在 IDE 里点一次、参数极多 → <strong>MCP</strong> 可更稳。</li>
<li><strong>会话已挂多少 MCP Server？</strong> 越多 → <strong>越应把高频执行迁到 CLI</strong>，给上下文减负；检索类仍可留给 MCP。</li>
</ul>
<p>认证也各有利弊：<strong>gh auth</strong> 适合「我就是这台机器上的开发者」；<strong>MCP PAT/OAuth</strong> 适合「IDE 内统一接入、多 Server 各管各的」——企业里两种都会并存。</p>
<blockquote>
<p>如下是Cursor结合了GitHub MCP和GitHub gh两种模式下直接修复GitHub Issue以及对已知PR的评审，可以说是很好的诠释了两者都有各自的应用场景。</p>
</blockquote>
<p><img src="https://assets.musecanto.com/uvxwY7KW9sGYbUfSojyke/sv-books/2026_05_25_editorimg_ecde3585-1e7f-45d8-be91-8675f8aa01ff.png" alt="image" loading="lazy" decoding="async"></p>
<p><img src="https://assets.musecanto.com/uvxwY7KW9sGYbUfSojyke/sv-books/2026_05_25_editorimg_0865e5ac-d17d-45e9-9d9b-ccf31245e6e2.png" alt="image" loading="lazy" decoding="async"></p>

<h2 id="我现在的做法">我现在的做法</h2>
<ul>
<li><strong>执行默认 gh</strong>：PR、CI、merge、本地 diff；规则里限制 Agent 为这类动作乱点 <code>merge_pull_request</code>。</li>
<li><strong>MCP 收窄</strong>：跨 repo 搜索、远端读文件、对话里开 issue；GitHub MCP <strong>留着，不承包执行层</strong>。</li>
<li><strong>Slash / Canvas 照用</strong>：接受「入口在 IDE、干活在终端」的产品形态——这和行业 CLI 化一致。</li>
<li><strong>减 Server 数量</strong>：比换更大模型便宜；把 MCP 当 <strong>插头</strong>，不当 <strong>唯一的手</strong>。</li>
</ul>
<p><strong>MCP 与 CLI 都会长期并存</strong>；<strong>趋势是 AI 应用在执行层更偏向 CLI</strong>——省 token、好调试、好组合、产品也在跟着 CLI 化。</p>
<p><strong>MCP 没死</strong>，但在分工上更像 <strong>标准化插头 + IDE 内能力目录</strong>；和 CLI <strong>抢的是层，不是命</strong>。真正要避免的，是用 MCP 做 <strong>gh 每天都做、且做得更好</strong> 的事——那不是否定 MCP，而是 <strong>把 MCP 从「胖执行层」放回「合适的层」</strong>。</p>
