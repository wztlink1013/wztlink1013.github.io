12:T2402,<p>前言：21.5 GB 内存压到 2 GB、开发服务器内存使用量最多可减少90%——Next.js 16.3 Turbopack 官方博客里的数字，足够让任何一个日常跑着 <code>next dev --turbo</code> 的人手痒。本文记录读完官方博客、又亲手本地升级留下的<strong>阅读记录</strong>——不是劝你别升，而是帮你分清「<strong>读官方升级博客该兴奋什么</strong>」和「<strong>升 preview 该警惕什么</strong>」。如果你也在等大版本、又不敢盲跟，下文有原文要点、我的实测踩坑，以及 stable 出来前我会怎么等。</p>
<hr>
<h2 id="原文在讲什么编译器性能补课不是新功能秀">原文在讲什么：编译器性能补课，不是新功能秀</h2>
<p>原文：<a href="https://nextjs.org/blog/next-16-3-turbopack" rel="noopener noreferrer">Turbopack: What's New in Next.js 16.3 (https://nextjs.org/blog/next-16-3-turbopack)</a>。这是 Next.js 16.3 Preview 系列第三篇（前两篇分别是 <a href="https://nextjs.org/blog/next-16-3-instant-navigations" rel="noopener noreferrer">https://nextjs.org/blog/next-16-3-instant-navigations</a> 和 <a href="https://nextjs.org/blog/next-16-3-ai-improvements" rel="noopener noreferrer">https://nextjs.org/blog/next-16-3-ai-improvements</a>）。核心信息可以收成四条：</p>
<ul>
<li>开发态<strong>内存使用量降低</strong>，长会话 dev 内存最高可<strong>降约 90%</strong></li>
<li><strong>构建阶段</strong>也能用文件系统持久化缓存（16.1 起 dev 已有）</li>
<li>实验性 <strong>Rust React Compiler</strong></li>
<li><code>import.meta.glob</code> 等工程化补齐，外加 HMR 冷启动、运行时体积、monorepo PostCSS 等</li>
</ul>
<p>官方立场很明确：Turbopack 的设计是<strong>增量编译</strong>——++编译成本和改动量成正比，而不是和整个路由树成正比++。为此早期做过取舍：<strong>多缓存在内存里，换更低 CPU</strong>。16.3 是在这个取舍上回调——内存可以降低到磁盘，不再无限涨。</p>
<h2 id="博客里最扎眼的数字内存和构建">博客里最扎眼的数字：内存和构建</h2>
<h3 id="开发内存编译-50-条路由之后">开发内存：编译 50 条路由之后</h3>
<p><img src="https://assets.musecanto.com/uvxwY7KW9sGYbUfSojyke/sv-books/2026_07_01_editorimg_1f11d41a-a8b6-4cc8-a265-d7f25da6053c.png" alt="image" loading="lazy" decoding="async"></p>
<p>实现路径：数据结构压缩 + 缩短缓存生命周期 + <strong>memory eviction</strong>（依赖 16.1 的 dev 文件系统缓存）。16.3 默认开启；排查时可关：</p>
<div class="code-block"><pre><code class="hljs language-ts"><span class="hljs-keyword">const</span> nextConfig = {

<p>官方也说了：降幅因路由图规模、会话时长、摸过多少路由而异，<strong>没有普适的 90%</strong>。</p>

<p>CI 思路：把上次 <code>.next</code> 带到下一次 job。</p>
<h3 id="其他博客要点">其他博客要点</h3>
<ul>
<li><strong>Rust React Compiler</strong>：大应用 compile 收益 20%–50%（实验性，需 <code>turbopackRustReactCompiler: true</code>）</li>
<li><code>import.meta.glob</code>：Vite 兼容 API，仅 Turbopack，不走 <code>--webpack</code></li>
<li><strong>HMR</strong>：大应用冷启动快 15%+</li>
<li><strong>兼容性</strong>：Windows <code>import.meta.url</code>、<code>createRequire</code>、chunk 重试、Safari CSS HMR 等</li>
</ul>
<p>读到这里，我的第一反应和很多人一样：内存和构建数字都好看，值得升级——尤其对我<strong>MuseMVP</strong>和<strong>MuseCanto</strong>两个大型MonoRepo项目日常开着 dev、32G内存常常顶满的情况，官方那组「<strong>开发服务器内存使用量最多可减少90%</strong>」的数据实在诱人。于是我去试了 preview。</p>
<h2 id="项目实测升到-1630-preview5windows-上先踩刹车">项目实测：升到 16.3.0-preview.5，Windows 上先踩刹车</h2>
<p>实测是在自己的 Next.js 16 App Router monorepo 上做的——<code>package.json</code> 里 dev 脚本是 <code>next dev --turbo</code>，版本已跟到当前最新稳定线16.2.9。试升级时把 <code>next</code> 改成 <code>16.3.0-preview.5</code>，<code>pnpm install</code> 后本地 <code>pnpm dev</code>，终端会显示类似：</p>
<p><img src="https://assets.musecanto.com/uvxwY7KW9sGYbUfSojyke/sv-books/2026_06_30_editorimg_df3465da-6639-4f31-b452-a1b328d383fe.png" alt="Snipaste_2026-06-30_21-36-23" loading="lazy" decoding="async"></p>
<p>没有改 webpack，也没有关 Turbopack——就是想看博客里那套默认路径在<strong>我自己的 Windows 环境</strong>里表现如何。</p>
<h3 id="我实际遇到了什么">我实际遇到了什么</h3>
<p>说实话，<strong>没有跑完「官方 benchmark 那种理想路径」</strong>。</p>
<p>在 Windows 本机（Win10/11，日常开发机）上，preview 版暴露出一些问题——其中有像是<strong>旧版本已经修过、preview 又冒出来的 regression</strong>。具体表现我打算用截图贴在公众号里（终端报错、异常页面、版本信息），这里用文字概括观察到的几类现象，避免空口编 stack trace：</p>
<ol>
<li><strong>dev 链路不稳定</strong>：并非「一启动就挂」，而是在正常开发节奏下（改文件、切路由、触发热更新）出现此前 16.2 稳定版没有的行为；有的场景需要重启 dev server 才能恢复。</li>
<li><strong>和博客「兼容性修复」的预期有落差</strong>：原文专门提了 Windows 上 <code>import.meta.url</code>、chunk 重试等修复——我这边仍踩到平台相关的问题，说明 <strong>preview 离「默认放心升」还有距离</strong>。</li>
<li><strong>不只看自己</strong>：在 X 上反馈，也有相关开发人员正在调查中。</li>
</ol>
<p><img src="https://assets.musecanto.com/uvxwY7KW9sGYbUfSojyke/sv-books/2026_07_01_editorimg_a284a17a-8ec3-4c04-961f-f660cd9a3fe9.png" alt="image" loading="lazy" decoding="async"></p>
<details open>
<summary>基于此</summary>
<p>16.3 博客讲的是方向和 benchmark，++不是「今天就能升生产」++。preview 在 Windows 上的回归，足够让我把两个项目继续留在当前稳定版，只把 16.3 preview 当本地观察分支。</p>
<p>os error 5的问题多是window缘故，mac用户可以尝试一下更新一下</p>
</details>
<h2 id="收束读博客有价值升-preview-要克制">收束：读博客有价值，升 preview 要克制</h2>
<p>官方博客把 Turbopack 16.3 的<strong>设计回调</strong>讲清楚了：从「<strong>内存换 CPU</strong>」走向「<strong>内存使用量最多可减少90%、构建可落盘</strong>」。数字好看，方向也对。</p>
<p>但作为读完原文又去试 <code>16.3.0-preview.5</code> 的人，我目前的结论是：</p>
<ul>
<li><strong>读</strong>：推荐阅读原文，搞懂配置项和取舍</li>
<li><strong>试</strong>：可以在分支上本地玩 preview</li>
<li><strong>升</strong>：生产级应用，尤其 Windows + 大 monorepo，<strong>我建议再等 stable</strong>，至少等我这类 regression 在 release note 或社区里被确认修掉</li>
</ul>
<p>增量编译的账，不只在快不快，还在<strong>升级后能不能安心写一下午代码</strong>——我这边 preview 还没过这条线，但 memory eviction 一旦 stable，我还是会第一时间在 <strong>MuseMVP</strong> 和 <strong>MuseCanto</strong> 上验证。</p>
